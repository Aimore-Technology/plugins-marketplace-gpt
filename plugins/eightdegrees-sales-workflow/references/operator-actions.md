# Dedicated operator action pages

## Purpose and entry point

The operator needs to find this task's answers and decision without scrolling past technical database properties. Keep ONE PendingTasks database as the canonical execution record, and create ordinary pages under `Aimore/Actions` for human input. These are not another tracker or new Form response rows. Ordinary pages have only the title property; IDs, actors, versions and execution fields stay in PendingTasks and its workflow-owned history.

Use the packaged [action page layout](../assets/task-action.md), rendered in the saved workspace language. The Actions hub groups links to active pages by the five existing categories. Show customer/topic, a short business status and the requested action. Use it as the primary human entry from root navigation, reports and notifications; retain a secondary link to the canonical task for troubleshooting.

Keep active links ahead of historical child-page listings; do not turn a long list of superseded pages into the new primary queue. Preserve history and native child-page tags when updating the hub. If page creation/registration is uncertain, retain any returned page ID and reconcile the original parent/task before retrying; a failed URL projection must not create another action page.

PendingTasks views may show Name, State, Category, Mode and ActionPageURL, hiding technical IDs when supported. A native database card/title may still open the database record: do not claim that its click target was changed. The visible action link and ordinary-page hub provide the direct route. Views/hiding are presentation, not access control. If tools cannot create/register an ordinary page, report action-page setup incomplete and offer the original task or an explicit chat reply; do not claim the clutter is fixed or invent widgets.

## One page for one task step and review version

Register ActionPageURL and ActionFormVersion=`task-action-v1` on the canonical task. In workflow-owned task history, bind the actual action page ID to TaskId, StepId, Category, Mode, ContentVersion and exact review payload/manifest digest when relevant. This binding is system-owned; never ask the operator to copy an ID/version, type ApproverId or choose their own authority. Resolve actor from existing configured/authenticated evidence, distinguishing observation from actual decision time.

Reuse the registered page while task/step/content is unchanged. For new review content or a new approval step, create and register a new action page, preserve old input/decisions, mark the old page superseded and remove its active link from the hub. Never transfer checked choices to the new page. A copied/unregistered page or a superseded page cannot approve the active task. Customer-readable titles may include topic/short date to distinguish multiple tasks; matching still uses the registered IDs.

## Only relevant inputs

At the top show the customer/topic, what is needed, current business status and the effect of submitting. Put a brief business summary and direct exact source/preview links above the input controls; long review material may follow the controls or remain at that exact linked destination. Do not put an ID table, empty technical properties, full execution history or a long raw Notes audit header before the controls.

| Category | Display and editable input | Decision meaning |
| --- | --- | --- |
| ClientMatching | Human-readable verified candidates with email/phone; select one candidate or none; additional matching data only when needed | Submit a customer choice for CRM verification; never auto-create a contact |
| DataCompletion | Only the missing required/conditional fields, with optional fields labeled; native paragraphs for long answers | Submit supplied information for validation; not factual or send approval |
| ContentReview | Exact current Notes/persona proposal, conflict alternatives or draft; clear changes from prior version; revision-comments area | One of Confirm content, Return for revision, Pause, Postpone or Cancel, as applicable; no send approval |
| SendApproval | Exact sender/recipients, subject/body, usable matching preview/files, source and send window | Explicit Approve this send, Pause, Postpone or Cancel; content confirmation never maps to Approve |
| ExecutionExceptions | Business explanation, what is already known, recommended next verification and only the missing evidence | Request reconciliation, keep paused or cancel; never a blind retry or a user-declared provider success |

Show the few applicable choices as native Notion to-dos, all initially unchecked, with an instruction to choose exactly one per labeled choice group. Submission and reminder-receipt to-dos are not decision options. Validate candidate selection and review intent separately if both groups are needed. Notion to-dos are not radios: validate zero/multiple selections rather than pretending exclusivity is enforced. No generic Confirm label for actual sending. Candidate-to-contact and localized-label-to-decision mappings live in the canonical binding, not editable user-supplied IDs.

After answers/selection/comments, place one separately named submission to-do: for example Submit supplied information, Submit content decision or Submit send decision. Explain that Notion saves edits automatically, but this checkbox requests processing only when an authorized workflow next runs. It is not a custom button, immediate execution or a new scheduled job. Do not precheck a decision or submission. Native paragraphs are multiline editors; do not promise a custom textarea widget.

Keep the actual versioned review material inline when practical, or immediately linked with the exact same-file preview. Changes requested here are revision input, not edits silently applied to approved bytes. If review material or the approved manifest changes, prepare a new content version and action page before accepting a decision. Action pages do not replace the CRM plain-text template or HTML approval contract.

When a reminder exists, a separate Acknowledge receipt to-do may be shown with its ReminderKey bound internally. Its label states that it closes only reminder chasing. It does not submit answers, confirm content, approve sending or continue a Manual task.

## Observe, validate and record

1. Discover eligible canonical Automatic tasks, then fetch each registered active action page once for candidate input, reusing that snapshot until the required final reread. Do not filter new-route candidates solely by the old InputSubmitted projection: the human now checks a body to-do. Do not scan every historical action page or fetch Manual forms from run-auto. Verify binding/current payload and actual saved checkbox/answers; a view row, page edit time or legacy Decision edit is not new submission. Leave unsubmitted drafts untouched. A page open/save is not a decision. Any unexamined eligible forms mean partial input coverage, not a zero-pending claim.
2. Preserve the existing Mode and invocation limits. A scanner cannot process a Manual task's form/decision or take it over. For Manual work, show a ready-to-copy owner-skill `continue <action page URL>` request after submission; the operator must explicitly invoke that continuation. Resolve the page's original-task backlink, then verify that the task's active ActionPageURL and binding match; a copied page backlink alone is insufficient. No notification, customer send or schedule is enabled by submission.
3. On a submitted form, validate exactly one applicable choice in each required choice group, required answers, conditional fields and any postponement date/timezone. Return for revision requires useful revision instructions. No applicable choice/multiple choices/missing fields means NeedsCorrection. Explain each field error next to the input, preserve every answer/selection/comment, and clear only the submission to-do if the input still matches the rejected snapshot. Do not make a decision for the operator.
4. Reread task, active binding and action inputs before accepting. If input/submission is changed or withdrawn, do not consume stale data. Persist the exact observed submission snapshot, action-page ID, binding/version, actor evidence and observation time in the original task/log BEFORE any dependent business mutation. Key a submission by action-page ID plus a stable digest of its binding, answers, selected intent and comments. Exclude workflow-owned status text, observation times and the consumed submission checkbox from that input digest; retain checkbox evidence separately in the snapshot. Serial re-observation of an already applied snapshot cannot duplicate an action. Notion is not an atomic lock.
5. Copy an applicable validated decision/version/actor and a short input summary to canonical properties as workflow-owned projections. Candidate/data submission never creates Confirm/Approve. Request reconciliation stays a snapshot intent, not a new select option or permission to repeat an unknown external attempt; leave unrelated Decision fields unset. Receipt updates only reminder evidence. Failed canonical evidence saving blocks dependent writes. Record accepted input and apply/read back via the owner workflow and existing pending-input/CRM/send rules.
6. After durable acceptance, clear the consumed submission to-do only if the action page still matches the accepted snapshot. Keep the selected choice and answers visible with a status such as Decision recorded; execution pending. A cleared checkbox after documented consumption does not erase the recorded decision. Later answer/choice/payload edits invalidate pending use of that snapshot and need fresh submission/review as applicable. A new submitted Cancel/Pause or explicit withdrawal is checked before the dependent action. Re-fetch both original records before an external write/send; compare the accepted snapshot to current input and binding, in addition to ordinary approval/stop checks.
7. Show the actual outcome and next step at the top. On success retain answers/history; on partial saving repair only the missing projection. Never repeat a provider write to repair this page. New content after Return uses a new page/version with blank choices. Paused/postponed work does not resume just because data was edited; require a new explicit owner-workflow continuation and any renewed approval/window. Completed/cancelled/superseded pages show No action required and no active submission controls. Old checkbox edits on those pages do not reopen tasks.

If page access is denied or input is ambiguous, keep that task waiting with a recovery explanation. Present unavailable preview/expired approval as such, retaining draft/comments and a clear request for a fresh review. Do not present unverified application as complete.

## Existing workspaces

An explicit init upgrade creates/reuses Actions and action pages for eligible open tasks, registers bindings/links and preserves task/page/run IDs, input, history and Mode. Do not delete/convert technical properties or move business records out of PendingTasks. Show old details behind a link.

Copy only unambiguous existing answers as unsubmitted draft input, retaining the original answer/provenance. Never manufacture a new human submission or decision. Existing approved snapshots remain historical valid evidence within their original scope; migration alone neither approves nor revokes them. An in-flight/unconsumed legacy submission, unresolved projection or unclear decision binding stays on its legacy input route until reconciled by the owning workflow; mark that task's action migration pending rather than introducing two editable authorities. For successfully migrated tasks the action page is the sole new-input surface; original properties are projections. Closed tasks remain historical without generating new action forms.
